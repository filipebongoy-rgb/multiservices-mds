# Contrat MDS — pour modules développés en parallèle

Routeur racine `mds` dans `server/routers.ts`. Sources communes : `shared/mds.ts`. Schémas et helpers partagés non modifiés sans coordination.

`mds.catalog.list({includeInactive?:boolean})` → Service[] ; inactive seulement admin, public actifs exclusivement. Service champs schema + id, createdAt, updatedAt. `save(serviceSchema)` → Service ; `remove({id})` → success. Catalogue initial 34? utiliser liste réelle des 5 familles shared/mds.ts, entièrement inactive.

`mds.settings.public()` → {zone, contactEmail, contactPhone, businessAddress, legalName, legalNotice, proposalExpiryHours}. Valeurs inconnues vides. `get()` admin même + paramètres ; `save({zone,contactEmail,contactPhone,businessAddress,legalName,legalNotice,proposalExpiryHours})` admin.

`mds.claimArtisan({code:string})` protected → success. Activation unique réservée au détenteur d’un code secret généré lors du seed (hash en base), fichier privé hors Git `/home/ubuntu/mds-artisan-activation.txt`. Pas de premier visiteur admin ; OWNER_OPEN_ID absent de l’environnement. Atomicité verrou principal unique, journal.

`mds.requests.create(createRequestSchema)` public → {id, reference, trackingToken}. Création transactionnelle/idempotente, to_analyze si libre, awaiting_mds sinon, événement sent puis état réel. Champs Request exposés : id,reference,serviceId,serviceName,description,problemType,name,email,phone,address,postcode,city,desiredStart (Date|null),organizationId,siteId,answers,status,version,proposedStart(Date|null),proposedPriceCents(number|null),durationMinutes(number),proposalMessage(string|null),expiresAt(Date|null),quoteStatus('none'|'pending'|'accepted'|'refused'),createdAt,updatedAt. trackingToken/hash/key ne jamais exposer sur listes/details.

`mds.requests.track({reference,token?})` → {request, events, documents, appointment, reviews}. Sans token utilisateur doit propriétaire demande, membre organisation ou admin. events {id,requestId,status,message,actorType,createdAt}. documents {id,name,mimeType,kind,createdAt}, aucune clé privée. appointment {id,startAt,endAt,status} ou null. reviews {id,authorType,rating,comment,moderation,createdAt}.
`mds.requests.mine()` protected → Request[] ; `list()` admin → Request[] ; `detail({id})` protected scoped → même détail que track.
`mds.requests.claim({reference,token})` mutation protected → success. Rattachement explicite d’une demande individuelle invitée : clé de suivi exacte ET email OAuth présent correspondant (trim/minuscules), transaction verrou principal et demande, propriétaire nul ou même utilisateur idempotent, organisation interdite. Associe utilisateur/client/notifications, audit et événement sans changement inventé de statut ; version actualisée. Aucune récupération par email seul. Pour toute demande d’organisation, appartenance active obligatoire à chaque accès, action et document, y compris ancien auteur : un token ne remplace jamais cette appartenance ; seul l’unique artisan principal bénéficie de l’accès transversal.
`mds.requests.artisanAction(artisanActionSchema)` admin → success : accept/refuse/propose/information/quote/start/complete/cancel/invoice/paid/close. Conditions server ; propose/accept exige créneau/prix ou service configuré ; devis distinct si complexe. Aucune facture émise sans vrai document ! Si action invoice/paid non implementable justement rejeter plutôt que simuler. Rendez-vous confirmé seulement confirm client, atomicité conflit planning MDS.
`mds.requests.clientAction(clientActionSchema)` public avec token ou identité scoping → success. confirm/refuse/reschedule/information/acceptQuote/refuseQuote/cancel. version mismatch CONFLICT, double confirm idempotent sans doublon RDV. Expiration réelle vérifiée et enregistrée, interne notifications à chaque événement.

`mds.organizations.list()` protected → {id,name,type,role}[] ; create({name,type}) → {id}, types entreprise/syndic/bailleur/gestionnaire/association/collectivite ; detail({id}) → {organization,sites,members,invitations,requests,documents,contracts}. sites {id,name,address,postcode,city,contactName,contactPhone} ; members {id,userId,name,email,role} ; invitations {id,email,role,createdAt}, pas de token secret stocké réexposé. contracts {id,name,status,startAt,endAt,documentId}. addSite({organizationId,name,address,postcode,city,contactName,contactPhone}) ; invite({organizationId,email,role:'manager'|'member'}) → {invitationCode} code manuel (pas email fictif) ; join({code}) vérifie email OAuth ; removeMember({organizationId,userId}) manager autorisé mais pas propriétaire.

`mds.documents.upload({reference?,token?,organizationId?,name,mimeType,base64,kind:'photo'|'quote'|'invoice'|'contract'|'other'})` → {id}. 5 Mo, JPG/PNG/WebP/PDF, contrôle signatures, chiffrement AES-GCM/clé aléatoire par document stockée serveur DB ; attach auth avant transfert, guest photo seulement propre request/token. Devis/facture admin seulement. `mds.documents.download({id,reference?,token?})` → {base64,name,mimeType} pour restitution privée tRPC avec auth Android fallback ; no-store et aucune clé/URL ciphertext dans API. `mds.reviews.submit({requestId,rating:1..5,comment?:string})` protected ; côté admin = artisan, sinon user doit demande propriétaire ou organisation autorisée, terminé uniquement, unique par rôle et requête, moderation pending privé. `mds.notifications.list()` protected → {id,title,message,requestId,readAt,createdAt}[] ; `read({id})`. `mds.audit.list()` admin → {id,action,entityType,entityId,createdAt}[] ; `mds.appointments.list()` scoped protected → appointments avec reference,requestId,startAt,endAt,status,name,address.

Erreurs françaises. Aucun objet factice ou acteur simulé. Les tests unitaires de workflow peuvent mock DB ; migrations/seed uniquement configuration inactives et activation réelle, aucun faux client.

Précisions de transport : `mds.documents.download` est une mutation tRPC, à appeler via `useMutation().mutateAsync` (pas `utils.download.fetch`), pour ne pas placer de document privé en cache de requête frontend. Les réponses API sont `private, no-store`. La capacité de suivi utilise une clé aléatoire applicative indépendante, persistée dans les réglages serveur et jamais exposée ; elle ne dépend pas de la rotation des JWT de la plateforme.
